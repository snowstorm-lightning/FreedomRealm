# 项目愿景与核心原则

## 新定义

AI-HRMS 是 AI 时代的人类与智能体资源管理系统。它为个人、多人协作组织、社区、开源项目、小型工作室、合作社、企业内部团队和更复杂组织提供统一的工作执行与治理底座。

AI-HRMS 把 `HumanActor`、`AgentActor`、`WorkItem`、`ToolContract`、`ApprovalGate`、`PolicyRule`、`Observation`、`LearningArtifact`、`ProjectInstance` 和 `DomainWorkflow` 统一管理，让标准化工作可以在明确约束下由 AI 执行，由人类设定目标、定义边界、审批高风险动作、审查结果和承担最终责任。

当前项目仍然叫 AI-HRMS，本轮不处理正式更名。

## AI 时代 HRMS 的边界扩展

传统 HRMS 管理员工、组织、考勤、档案、审批和协作内容。AI 时代的 HRMS 还必须管理：

- 人类参与者和社区成员。
- AI 智能体。
- 技能、工具和工具契约。
- 任务、审批、策略、预算和审计。
- 评测、观察、失败案例和学习沉淀。
- 模板、实例成员、实例权限和跨实例协作关系。
- 资源档位、模型路由和自适应任务调度。

这不是放弃 HRMS，而是重新定义 HRMS，使其具备 AI 时代的灵活性、扩展性和社区适应性。

## 愿景

绝大多数标准化工作都可以逐步交给 AI 在明确约束下完成。人类应减少重复执行工作，保留目标设定、边界定义、高风险审批、结果验收、系统修正、社区治理和最终责任。

AI-HRMS 要成为这样的系统底座：

- AI 执行、分析、生成候选、调用工具、整理反馈、沉淀样本。
- 人类设定目标、判断价值、定义边界、审批高风险动作、治理社区和承担责任。
- 每个动作可追溯。
- 每个高风险动作可审批。
- 每次失败可复盘。
- 每个改进可评测。
- 每次发布可灰度和回滚。
- 每个 ProjectInstance 可由一个人运行，也可由多个人共同运行。
- 多个 ProjectInstance 可以在授权、信任、审计和数据分级约束下协作。

## 优先服务对象

- 个人。
- 自由职业者。
- 开源维护者。
- 小团队。
- 社区组织。
- 多人协作体。
- 合作社和工作室。
- 企业内部团队和强治理组织。

企业私有化部署继续保留为 `Enterprise Mode`，但项目方向不能被商业公司重定向。

## v1 范围

- 聚焦 AI-HRMS Core、ProjectInstance、最小人机协作闭环和强治理边界。
- 先建设控制面、运行面、审批面、审计面、学习飞轮、自适应运行和传播闭环。
- 保留传统 HRMS 能力，特别是组织、账号、员工档案、考勤、权限和协作内容。
- 支持 Tiny / Demo / Local / Community / Enterprise 的运行档位定义。
- 定义 Federation、Commons 和跨实例协作边界，但不实现完整分布式计算网络。

## v1 成功标准

- 人类、智能体、工具、审批、审计和 ProjectInstance 都拥有独立身份与清晰边界。
- 每个高风险动作都能追溯到 `WorkItem`、`ApprovalGate`、策略判断、操作者和回滚路径。
- 每次 `AgentRun` 都能说明输入上下文、可用工具、预算、模型路由、输出、异常和人工介入点。
- 每个进入生产的 prompt、workflow、策略或模型路由变更都经过 `staging` 评测、人工审批、灰度和回滚设计。
- HR 核心事实由控制面维护，智能体只能提出建议、生成候选或在授权边界内执行工具。
- 个人和社区可以用 Tiny、Demo 或 Local 档位理解并运行最小闭环。
- 多人实例可以通过 Community Mode 建立成员、权限、审批和模板共享。
- Enterprise Mode 能在强隔离网络中运行，并通过受控网关访问外部模型或服务。

## 失败信号

出现以下情况说明系统设计或实现已经偏离本项目原则：

- 模型输出可以绕过控制面直接修改员工、薪酬、合同、权限或审批事实。
- Agent Runtime 持有 HR 主数据真相，或绕过 Temporal 自行完成长流程状态推进。
- 新接口、新事件或新字段没有同步记录请求边界、响应边界、事件语义和审计点。
- 生产学习结果没有评测基线、审批记录、灰度范围或回滚版本。
- `dev`、`ci`、`staging`、`prod` 复用数据库、模型 key、OIDC client、AgentActor 身份或长期记忆。
- 审计日志只记录“发生了什么”，无法说明“谁、为什么、基于什么策略、可如何恢复”。
- 跨实例协作默认共享私有数据或允许远程实例直接调用本地高风险工具。
- 资源降级导致审批、安全、审计、预算或数据分级被绕过。
- 项目被改写成泛泛 agent framework，传统 HRMS 能力和人类责任边界被弱化。

## 非目标

- v1 不实现完整分布式计算网络。
- v1 不做多租户商业 SaaS。
- v1 不承诺完全无人自治组织。
- v1 不绑定单一模型供应商。
- v1 不默认上传用户私有数据。
- v1 不让跨实例协作绕过审批和审计。
- v1 不从零构建全套 ERP/CRM/财务系统。
- 本轮不处理项目正式更名。

## 核心原则

### 1. Humans steer, agents execute

人类负责目标设定、价值判断、边界定义、高风险审批、结果验收、社区治理和最终责任；智能体负责执行、分析、拟议、自动化和反馈整理。

### 2. Repository is the system of record

系统规则、设计决策、评测基线、执行计划、开源策略和社区治理必须进入仓库，不能只存在于会议记录、即时聊天或脑内知识。

### 3. Legibility over cleverness

优先选择对未来人类和未来智能体都可理解的结构、命名和边界，而不是短期最炫的实现。

### 4. Controlled evolution

系统必须能够学习，但学习结果进入生产前必须经过评测、审批、灰度和回滚。

### 5. Policy before autonomy

先定义身份、工具边界、预算、风险等级、数据分级和审批策略，再扩展智能体自治能力。

### 6. Durable workflows by default

长流程、人工介入、补偿逻辑和恢复路径不是异常场景，而是默认场景。

### 7. Open interfaces, replaceable providers

对上暴露稳定契约，对下保留模型、检索、观测、身份、存储和工作流组件的替换空间。

### 8. Local-first and instance-owned

个人和社区应能运行自己的 ProjectInstance。默认不上传私有数据，默认不依赖单一中心服务。

### 9. Commons before capture

长期价值优先沉淀在开放协议、模板库、评测样本、失败案例、复盘报告和贡献者声誉中，而不是沉淀到封闭平台。

### 10. Adaptive without safety bypass

系统可以根据资源、预算和模型可用性降级，但降级不能绕过审批、安全、审计、预算和数据分级。

## 人机分工

AI 适合承担：

- 样板代码。
- 文档草稿。
- API schema。
- ToolContract。
- 测试。
- 质量门禁检查。
- 一致性检查。
- 日志摘要。
- 失败复盘草稿。
- 模板生成。
- 重复性维护工作。
- 运行报告生成。
- 低风险任务执行。

人类适合承担：

- 愿景取舍。
- 价值判断。
- 真实用户需求判断。
- 高风险审批。
- 安全与伦理边界。
- 社区治理。
- 冲突处理。
- 许可证和商标决策。
- 最终责任承担。
- 对哪些工作应交给 AI 的判断。

原则：

- 人类可以退出重复执行。
- 人类保留目标、边界、责任和高风险判断。
- AI 执行必须受策略、预算、权限、审批、审计和回滚约束。

## 设计取舍

- 优先明确治理边界，再追求自动化深度。
- 优先使用可回放、可审计、可恢复的流程，而不是一次性脚本式自动化。
- 优先把复杂度放在契约、策略和评测中，而不是让模型自由发挥。
- 优先支持个人和社区的低门槛运行，同时保留企业强治理架构。
- 优先让文档、ADR、执行计划和评测基线成为后续代码仓实现的输入。
