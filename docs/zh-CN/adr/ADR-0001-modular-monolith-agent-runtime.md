# ADR-0001: 采用模块化单体控制面 + 独立智能体运行面

## 状态

Accepted

## 背景

项目当前处于 v1 架构起步阶段，目标是尽快建立可生产演化的业务边界、审批治理和 agent 协作底座。若从第一天就拆分大量微服务，会引入过高的运维和一致性成本。

## 决策

- 控制面采用模块化单体
- 智能体运行面独立部署
- 通过明确定义 API 与事件边界保持后续拆分空间

## 实施约束

- 控制面模块必须保持清晰边界，跨模块协作通过应用服务、领域事件或显式接口完成。
- Agent Runtime 不持有企业主数据真相，只能读取授权上下文、执行 graph、调用工具并写回候选结果。
- 高风险动作必须回到控制面的 ApprovalGate 和审计模型。
- 后续拆分服务前，必须先证明模块边界、事件契约和数据所有权已经稳定。

## 后果

### 正面

- 更快建立核心业务与治理闭环
- 更低的跨服务一致性成本
- 更适合早期频繁调整领域模型

### 负面

- 控制面需要严格模块边界，避免退化为大泥球
- 后续如果组织扩大，需要评估按上下文拆分服务

## 验证方式

- 代码结构中存在明确的控制面模块边界。
- Agent Runtime 无法直接写 HR 主数据表。
- API 契约和事件前缀能映射到业务上下文。
- 关键流程的状态推进由 Temporal 或控制面管理，而不是散落在运行面脚本中。

## 替代方案

- 全量微服务：过早复杂化
- 单一大运行时：不利于治理和持久化长流程
